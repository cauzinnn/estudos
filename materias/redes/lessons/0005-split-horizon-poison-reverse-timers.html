Mitigação de Loops: Split Horizon, Poison Reverse e Timers

Omissão de rotas, envenenamento reverso com métrica 16, comportamento em loops de 3 nós e temporizadores do RIP.

← Disciplina ← 0004: Instabilidades Ficha: Algoritmos de Roteamento

1. Split Horizon Simples (Horizonte Dividido)

A regra do Split Horizon simples parte de uma premissa lógica trivial:

"Se o nó A utiliza o nó B como seu próximo salto para alcançar o destino X, não faz nenhum sentido A anunciar a B que sabe chegar a X."

Na versão simples do algoritmo, o roteador $A$ omite completamente o destino $X$ de qualquer vetor de distância transmitido pela interface conectada a $B$. Como $B$ não recebe anúncio de $X$ vindo de $A$, $B$ nunca cometerá o erro de tentar alcançar $X$ passando por $A$ caso sua rota direta caia.

2. Split Horizon com Envenenamento Reverso (Poison Reverse)

No Split Horizon com Poison Reverse, em vez de simplesmente omitir a rota para $X$ no anúncio enviado a $B$, o nó $A$ anuncia explicitamente:

$$D_A(X) = \infty \quad (\text{Métrica } 16)$$

  • Vantagem: Elimina ambiguidades imediatamente. Se $B$ perder a rota direta para $X$, $B$ sabe categoricamente que $A$ é uma rota "envenenada" ($\infty$), quebrando loops de 2 nós no primeiro instante, mesmo se pacotes forem perdidos.
  • Trade-off: Como não há omissão de entradas, os pacotes de atualização transportam mais dados, consumindo ligeiramente mais banda de controle.

3. A Pegadinha Fatal: Onde o Split Horizon Falha!

Uma das maiores fontes de erro em exames de redes é assumir que o Split Horizon resolve todos os loops de roteamento.

⚠️ O Calcanhar de Aquiles: Ciclos de 3 ou Mais Nós

Considere três roteadores em anel: $A \to B \to C \to A$. Cada um aprende a rota para um destino através de uma interface diferente daquela pela qual ele transmite para o próximo vizinho do anel. Como a rota não está sendo enviada de volta pela mesma interface de entrada, o Split Horizon não atua! O loop circular de 3 nós persiste e o algoritmo continuará contando até o infinito (16).

4. Atualizações Disparadas (Triggered Updates)

No RIP comum, os nós transmitem anúncios a cada 30 segundos. Se um enlace cair no segundo 1, esperar até o segundo 30 para avisar os vizinhos daria tempo suficiente para que roteadores adjacentes espalhassem rotas obsoletas.

As Triggered Updates (Atualizações Disparadas) rompem esse atraso:

  • Assim que uma métrica de rota sofre alteração (especialmente quando uma rota cai e passa para 16), o roteador gera e envia imediatamente um vetor de atualização, sem aguardar o temporizador periódico!
  • Isso faz as "más notícias" viajarem muito mais depressa, reduzindo a janela de tempo em que loops podem se consolidar.

Exercício 4: Mecanismo de Anúncio Imediato

5. O Ciclo de Vida de uma Rota: Os Temporizadores do RIP

O RIP emprega três temporizadores rigorosamente orquestrados para gerenciar rotas:

  • Periodic Timer (30s): Intervalo regular de envio de vetores completos (com uma variação aleatória de jitter de $\pm 5$s para evitar sincronização em fase).
  • Route Timeout / Invalidation Timer (180s): Se nenhuma atualização for recebida para uma rota por 180 segundos, o roteador assume que o destino caiu e marca sua métrica como 16 ($\infty$). A rota entra em estado de lixo.
  • Garbage Collection / Flush Timer (120s): Período adicional de 120s durante o qual a rota continua sendo anunciada aos vizinhos como inalcançável (métrica 16). Ao expirar, a rota é permanentemente excluída da tabela.
